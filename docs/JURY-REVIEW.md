# Критичний суддівський перегляд · 7 жовтня 2026

Це внутрішня перевірка за офіційними критеріями, а не оцінка журі чи прогноз
перемоги. Історія попередніх перевірок: [VALIDATION.md](VALIDATION.md).

## Вердикт

**Сильний локальний прототип; конкурсне подання поки NO-GO.** Реальні Qloo
пошуки, ranking, P00 та детермінований сценарій підтверджені. Додано й
перевірено MCP-інструмент для наявного агента без OpenAI API. Його викликав
програмний клієнт: робота зовнішнього LLM-агента, користь для людей,
публічний код і зовнішнє демо ще не підтверджені.

За [правилами](https://qloo.devpost.com/rules) застосунок має поєднувати Qloo
з агентним інструментом, фреймворком або наявним агентом. Чотири критерії
мають однакову вагу. MCP — конкретний шлях до агентного інструмента;
відповідність першому етапу визначають організатори. Робочий протокол
сам по собі не доводить поведінку LLM чи якість рекомендацій.

## Що витримує перевірку

| Критерій | Підтверджена сильна сторона | Головна прогалина |
| --- | --- | --- |
| Технологічна реалізація | Реальний Qloo, whitelist книг, незмінні складські факти, версії рішень, бюджет викликів, MCP | Зовнішній агент ще не пройшов сценарій; OpenAI planner блокується балансом |
| Дизайн | Brief → добірка → уточнення → картка; описи книг, проста записка, мобільні перевірки й recovery | Незалежного проходження покупцем та доказу кращого вибору немає |
| Потенційний вплив | Конкретна задача заміни недоступного подарунка в межах полиці й бюджету | Склад симульований; немає партнера, результатів користувачів або оцінки доречності |
| Якість ідеї | Культурні смаки перетинаються з доступними виданнями та обмеженнями | Не доведено перевагу Qloo над простим сортуванням або агента над статичним Qloo |

MCP відхиляє вигадані або позичені taste IDs, непідтверджений brief, зміну
складських фактів через аргументи, старі версії та повторний запуск briefId.
Сесійні й денні ліміти застосовує чинний сервер. Прапорець підтвердження
людиною — твердження клієнта, а не незалежний доказ.

Перевірка знайшла експлуатаційну проблему: процес завершився, залишивши
lock. Додано read-only діагностику й явне відновлення, що перевіряє відсутність
PID та зберігає старий запис. Сервер відновлено у `qloo_only`. Початкову
MCP-відмову збережено; виклики не витрачались. Успішний прохід змінив
ledger з 12 до 17, не підвищуючи ліміту.

У первісному MCP-проході UI та ядро не змінювалися. Пізніше цього дня
додано описи й просту записку; нові браузерні перевірки та реальний HTTP
smoke пройдено для зміненої збірки. Копіювання перевірено в ізольованому
Chrome. Повний OpenAI/Qloo сценарій, Docker build, фізичний друк,
повний WCAG-аудит, навантажувальна стійкість і зовнішній HTTPS не підтверджені.

## Що я вимагав би перед поданням

1. **Робота агента:** підключити готовий MCP до наявного клієнта; зберегти
   справжній transcript із людськими підтвердженнями, викликами й відмовами.
   Не називати програмний smoke LLM-запуском. [Підключення](AGENT-MCP.md).
2. **Корисність:** зібрати незалежні оцінки й завершення задач. Benchmark
   collector реалізований, але 154 provider-результати та людські оцінки
   ще не зібрані. OpenAI-руки блокуються балансом. MCP не можна мовчки
   підставити замість замороженої Full-конфігурації. [Протокол](BENCHMARK.md).
3. **Продукт:** перевірити картку й добірки з покупцями та книжковими фахівцями.
   Короткі описи й проста записка вже реалізовані та технічно перевірені;
   їхню користь для людського вибору ще потрібно виміряти.
4. **Реліз:** публічний код з ліцензією, зовнішній HTTPS, перевірка з іншої
   мережі й доступність протягом оцінювання. Ліміт 60 викликів/день не
   підтверджує достатню місткість для журі.
5. **Матеріали:** нове англомовне демо фактично поданої збірки. Наявне
   fixture-відео не доводить live Qloo або участі агента.

Поточна підтверджена заява: **локальний Qloo-інструмент заміни подарунка
з жорсткими обмеженнями та перевіреним MCP-інтерфейсом**.
